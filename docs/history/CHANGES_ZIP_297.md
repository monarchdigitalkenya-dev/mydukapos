## Zip 297 - Table seating capacity, live occupancy, location badges, item-level QR cancel, kitchen/bar cancellation alerts

Built on the QR ordering that already existed (secure tokens, item + order notes, duplicate-order protection, cancel requests, WebSocket poke + polling) - nothing was rebuilt.
- **Sell from Store is now part of the Sales Counter search (Shop, Hotel, Hospital, Pharmacy, Production, Services):** the purple "Sell from Store" button and its pop-up are gone. Typing in the search box now also lists matching Store items under the inventory results (🏬 Store tag, code, quantity in Store, price). Tapping one takes 1 out of the Store (atomic `removeFromStore`), credits this branch and adds it to the cart; tap again for more. Store history still gets its Sold line when the sale is recorded. Limit: Enter/barcode scan sells inventory only - Store items are added by tapping.
- **Tables (Hotel):** each table has its own seats (add one table with name + seats, or set "Seats per table" when generating; change seats any time - managers/admin only; stored in the existing `pos_table_states` record, no migration). Rooms have no seats.
- **Occupancy at a glance:** every table/room card shows a status pill with icon AND text (Available / Occupied / Reserved / Needs clearing - rooms say Cleaning), seats, open-bill summary, and quick actions (Open table, View orders, View bill, Close session, Cleared - ready). Status filter chips with counts. Occupied is derived from the open session. A table with an open bill can't be released; settle, cancel and release are separate. New shop-wide switch "Tables need clearing after the bill is settled" (off = unchanged behaviour).
- **Badges everywhere:** `TABLE 07 - 4 SEATS - ORDER #1048` on kitchen/bar cards, waiter order cards, the cashier's waiting bills and settle screen, QR inbox and the printed kitchen/bar slip; rooms show the room; an order with no table/room says DIRECT ORDER / TAKEAWAY - nothing is invented.
- **Cancellations:** a guest can cancel ONE item (before the claim it comes off at once; after, a request the order's owner approves) and may give a reason; the total is recalculated server-side, one audit event, retries are one record. Kitchen/bar boards show a red CANCELLED alert (table, item, qty, reason, sound, "Seen") and a "CANCELLATION REQUESTED" banner on the table's card while staff decide. History is never erased. A cancel never marks a bill paid or releases a table.
- **Live:** the server pokes every till over the existing WebSocket on order, cancel and decision, and tills now poll immediately on a poke; plus a 3-second check while Service Orders / Kitchen / Bar is open (8 s otherwise). Kitchen/bar show a Live / Reconnecting indicator; the guest page re-checks every 4 s and warns when the connection is lost; a stale update can't revive a cancelled order (server-authoritative status).
- Files: `functions/api/qr-order.js`, `order/app.js`, `hotel/index.html`. Service worker `zip-297`. Tests: `table-occupancy-297` (9), `qr-item-cancel-297` (2).
- Not done / limits: Hotel only (other apps have no tables); QR codes are per table/room as before (regenerate exists); customer-page cancellations were verified on the server and by syntax check, not on a real phone; the guest page was not rendered in a browser; room "Cleaning" vocabulary unchanged; no browser-level end-to-end customer-to-kitchen test.
