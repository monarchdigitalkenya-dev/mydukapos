# Zip 159 - Hotel POS: dynamic categories, category chips, and Excel/CSV import

Scope: `hotel/index.html`. Shared code changed only for one sync field name (`inventoryCategories`). The version stamp and `hotel/sw.js` are untouched (bump on release).

## What changed

1. **Categories per inventory type, stored by id.** The types are never listed in the new code. They are read from `HOSP_INV_CATS` (minus "all"), `hospInvKindOf` and the records themselves. A type found only on a record shows up as an extra type. Existing types are not renamed, merged or removed. Types today: Item, Ingredient, Dish, Service, Utensil, Bar.
2. **Uncategorized** is a state (no `categoryId`, no `category`), not a category record. Nothing is ever lost.
3. **Category manager** (Inventory > "Categories & assign"): create, rename, activate/deactivate, reorder, delete-with-move (to another category of the same type, or to Uncategorized), search, and bulk-assign selected records. Records are never deleted. Every change is written to the admin activity log.
4. **Sales Counter and Service Orders (Orders tab)**: category chips above the grid. The chip is a real filter combined with the existing search, sort (best sellers first, then name) and stock rules (out-of-stock stays greyed / disabled). Screens use the same "what is sellable here" predicates as before. Grid is paged, 60 per page with "Show more". Pictures are lazy and async; a missing or broken picture becomes a placeholder. The selected chip is remembered per screen on the device.
5. **Category field** in the Add item form, the edit modal, the dish edit, and the utensil form (only the categories of that record's own type).
6. **Import** (per type from the Inventory screen, or "All"): xlsx (existing lazy SheetJS loader) and csv or pasted text; column mapping; category detection; preview before commit; per-row status; duplicate policy skip / update / create with per-row override; error rows are reported and never abort the rest; downloadable problem list.
7. **Sync**: new synced list `inventoryCategories` (client `registerSyncedField`, `collectSyncPayload`, `applyRemotePayload`, `MERGED` in `slimPayloadForPush`, `MERGE_BY_ID_FIELDS` in `functions/api/_merge.js`). Apps regenerated by `npm run sync`.
8. In-app guide entry and a "Categories and importing a list" chapter in `tools/build-guides.mjs` (`npm run guides` was run).

## Data model

Category record (`hospCategories`, localStorage `pos_inventory_categories`):
`{ id, kind, name, active, order, createdAt, updatedAt }`. A deleted category stays as a tombstone `{ id, kind, name, _deleted: true, updatedAt }`, so it cannot be resurrected by a stale device.

Records get `categoryId` plus `category` (the name, kept as a compatibility mirror so stations, offers, reports and anything else that reads `p.category` still work). Utensils (`pos_utensils`) get the same two fields.

Rules:
- A category belongs to exactly one type. Same name in two types = two categories. Same name (case, spacing and punctuation ignored) twice in one type is refused.
- A record whose `categoryId` is dangling or belongs to another type is treated as Uncategorized.
- Assigning a record to another type's category is refused.
- User-created ids are random (`cat-<kind>-<time><rand>`).

## Migration

Legacy `p.category` strings become **virtual** categories with deterministic ids `cat-<kind>-<slug>`, computed while indexing. Nothing is written on load. Two tills converge on the same ids without coordinating. A virtual category becomes a real record the first time a person acts on it (rename, reorder, assign, deactivate, delete, import into it). Rename also updates the name on every record of that category. It moves the kitchen/bar station setting and offer targets that used the old name, but only when no other record still uses the old name.

`hospCatKindOf`: `hospKind` if set; else "bar" for pours / kegs / bottles; else `hospInvKindOf`.

## Import behaviour

- Limits: 5,000 rows, 8 MB. Commit runs in chunks of 200 with a paint between them.
- Columns: known headers are matched offline first. The existing AI column reader is used only when no header is familiar, or when the button is pressed. Then a value-shape guess. The screen says which method was used. The user can always set columns by hand.
- Type: fixed in per-type mode (a Type column that disagrees puts the row in "attention" and it is not imported unless the user forces it). In "All" mode the type comes from a Type column, the user (per row, selected rows, or all), or a "Suggest types" button (built-in rules on price/quantity/cost). No row without a type is imported.
- Categories: matched per (type, normalised name) as existing, new (created only if ticked), or similar. **Similar names are never merged.** The import is blocked until the user chooses "same" or "different".
- Duplicates: by code, then name, then within the file. A match in a different type is "attention" and skipped. On update, stock quantities change only if ticked. A picture is set only if the record has none, unless "replace" is ticked. Only https links or existing `/api/media?` links are accepted as images.

## How to use

Inventory > pick a type tab > **Categories & assign** (manage, bulk assign) or **Import**. On the Sales Counter and in Service Orders, tap a chip; All clears the filter. Only managers, the owner, and staff with the Inventory or Add New Items role can manage or import. Other branches are read-only, even for the owner.

## Honest limitations

- No real browser, phone, touch device or printer was used. The layout (44 px chips, horizontal scroll, sticky bar) is CSS only and was not looked at on a screen.
- No real `.xlsx` file was read. The test stubs `window.XLSX`; real parsing depends on SheetJS from the CDN (needs the internet on first use).
- The perf test is a jsdom smoke test with generous budgets, not a device measurement.
- AI helps only with column mapping (existing service, optional). Type and category detection are deterministic rules; there is no AI type detection.
- Inactive categories hide their chip, but their records remain visible under All.
- The "bar" type is a view: bottle and keg items are counted under Bar for categories.
- The chip grid is debounced by 120 ms only when the inventory is over 400 items.
- The category index is rebuilt when the "dirty" flag set by `queuePush` or a pull is seen. A code path that edits the inventory and never calls `queuePush` would show stale chips until the next change.
- Pre-existing app behaviour (not changed): a device booted from old storage stamps all its synced records as fresh on its first push (the change snapshot is empty), so if it pushes before pulling, it can override newer server copies, including a delete tombstone. The test models a till that had been syncing before it slept.
- Sorting names uses lowercase comparison, not locale-aware collation.
